# OTP Implementation using Redis

Redis serves two distinct categories of use, both relevant here: caching reproducible data (fetchable again from the database if lost — e.g., job listings) and storing data with no other source of truth (e.g., OTPs, sessions), where Redis itself is the only place that data exists, and losing it means losing it permanently, not just incurring a performance cost. OTP falls into this second category, which is why `RedisTemplate`/`StringRedisTemplate` is the right tool — not `@Cacheable`, since there's no "method result" to cache, just direct, imperative control over storing, reading, and expiring a value.

`StringRedisTemplate` is a subclass of `RedisTemplate<String, String>`, not a separate implementation — it extends `RedisTemplate` and pre-configures `StringRedisSerializer` for keys, values, hash keys, and hash values, instead of the JDK default (`JdkSerializationRedisSerializer`). The actual API surface — `opsForValue().set()`, `.get()`, `increment()`, etc. — is identical either way, since `StringRedisTemplate` inherits all of it. The only real difference is what happens underneath: using plain `RedisTemplate<String, String>` without explicit serializer configuration would store both keys and values as unreadable, JDK-serialized binary data (not just values, as was the case in the Job entity caching work — plain `RedisTemplate` affects keys too, by default). `StringRedisTemplate` exists purely to avoid manually reconfiguring `StringRedisSerializer` every time for the common case where both key and value are plain strings.
